당신은 시니어 HTML5 Canvas 게임 개발자이자 게임플레이 시뮬레이션 엔지니어다.

지금은 구현하지 말고 Plan 모드로 아래 요구사항을 분석하고 평가하라.
파일을 수정하거나 새 파일을 만들지 말고, 프로젝트 구조와 에셋 폴더를 읽기 전용으로 점검한 뒤 설계 계획만 제시하라.

이 프로젝트의 장기 목적은 단순 관전형 레슬링 게임이 아니다.
캐릭터 스탯과 AI 설정을 바꾼 뒤 대량 전투 시뮬레이션을 수행하고, 승률·피해량·전투 시간·스킬 성공률 데이터를 분석하여 게임 난이도와 AI를 개선하는 반복 엔지니어링 루프를 만드는 것이다.

---

# 1. 프로젝트 목표

브라우저에서 동작하는 1대1 프로레슬링 자동 전투 시뮬레이션 게임을 설계한다.

기술 제약:

- HTML, CSS, JavaScript만 사용
- Canvas 2D 기반
- 외부 라이브러리 없이 구현
- Node.js 서버, 백엔드, 외부 API 없이 정적 웹 페이지로 실행 가능해야 함
- 향후 GitHub Pages 하위 경로 배포를 고려함
- 모든 리소스는 상대 경로를 사용해야 함
- 1990년대 저해상도 스포츠 게임풍 픽셀 아트 에셋을 사용함
- Canvas 이미지 보간을 비활성화하고 픽셀 아트가 흐려지지 않게 처리해야 함

첫 구현의 핵심은 다음 두 가지 실행 모드다.

1. 관전 모드: Canvas에서 P1과 P2의 자동 전투를 실시간으로 보여 준다
2. 결과 전용 시뮬레이션 모드: 렌더링을 생략하고 전투 결과 데이터만 빠르게 만든다

# 2. 에셋 구조

아래 폴더를 실제로 읽기 전용으로 확인하고, 파일명·확장자·이미지 크기·투명 배경 여부·스프라이트 프레임 구조를 분석하라.

```text
asset/
├─ gameboard/
├─ player_sprite/
└─ play_sample/
```

## 경기장 배경

경로:

```text
asset/gameboard
```

용도:

- 프로레슬링 링
- 링 뒤의 관중석
- 실내 경기장 배경

전투 화면의 중앙 배경으로 사용한다.

## 선수 스프라이트

경로:

```text
asset/player_sprite
```

동일 캐릭터의 가로형 스프라이트 시트가 있으며, 왼쪽부터 다음 4개 포즈가 배치되어 있다고 가정한다.

1. 스탠딩
2. 발차기
3. 밀기
4. 드롭킥

P1은 원본 스프라이트를 사용한다.

P2는 같은 스프라이트를 다음 방식으로 사용한다.

- 캔버스 좌우 반전으로 왼쪽을 바라보게 한다
- 가능하면 Canvas tint 또는 색상 변환으로 파란색 계열 팀처럼 표시한다
- tint 처리 품질이 낮거나 구현 안정성이 나쁘면 원본 색상을 유지한다
- tint 실패 여부와 관계없이 P2의 HUD 및 식별 색상은 파란색 계열로 유지한다

## UI 참고 이미지

경로:

```text
asset/play_sample
```

이 폴더의 샘플 이미지는 다음의 배치와 분위기를 참고하기 위한 자료다.

- 캐릭터 초상화
- 체력 바
- 분노 게이지 또는 스킬 게이지
- 남은 시간
- 전투 HUD 구성
- 하단 해설자 및 해설 영역

중요:

- 샘플 이미지를 게임 화면에 그대로 고정 배경으로 사용하지 않는다
- 실제 전투 상태를 반영하는 동적 HUD를 Canvas로 만든다
- 하단 해설자 및 해설 시스템은 첫 구현 범위에서 제외한다

# 4. 화면 및 성능 요구사항

## 논리 해상도

- 게임 내부 논리 해상도는 항상 `1920 x 1080`으로 고정한다
- 게임 세계 좌표, 링 경계, 충돌, 히트박스, HUD 위치, 스프라이트 위치는 논리 해상도 기준으로 계산한다
- 브라우저 실제 크기는 렌더링 단계에서만 논리 해상도에 맞춰 스케일한다
- 화면 크기와 FPS에 따라 전투 결과가 변하면 안 된다

## 화면 비율

- 게임은 항상 16:9 가로 비율을 유지한다
- FHD 환경에서는 1920 x 1080을 기준으로 선명하게 표시한다
- 스마트폰 가로 화면에서는 화면 크기에 맞춰 축소하되 비율이 깨지면 안 된다
- 남는 화면 영역은 검정 또는 짙은 색 레터박스로 처리한다
- 세로 화면에서는 억지로 세로 UI를 구성하지 않는다
- 세로 화면에서는 16:9 화면을 최대 크기로 유지하고, 필요하면 `가로 화면에서 플레이하세요` 안내를 표시한다
- 화면 회전 강제 API에 의존하지 않는다

## 픽셀 아트

- `ctx.imageSmoothingEnabled = false`를 적용한다
- CSS에 `image-rendering: pixelated` 또는 호환 속성을 적용한다
- 에셋 확대·축소 시 가능하면 정수 배율에 가깝게 처리한다
- 레이아웃은 반응형이어야 하지만 게임 내부 픽셀 아트의 비율과 모양은 유지되어야 한다

## 성능 목표

- 일반적인 데스크톱과 스마트폰 가로 화면에서 30 FPS 이상 렌더링하는 것을 목표로 한다
- 60 FPS 렌더링을 강제 요구사항으로 두지 않는다
- 성능이 낮은 환경에서도 전투 판정과 타이머가 느려지거나 빨라지면 안 된다
- 렌더링은 `requestAnimationFrame()`으로 수행한다
- 전투 로직은 렌더링 FPS와 분리된 고정 시간 간격으로 수행한다
- 기본 고정 업데이트 간격은 `1 / 60`초로 둔다
- 성능 저하 시 누적 시간을 이용해 필요한 시뮬레이션 업데이트를 반복 실행한다
- 한 렌더링 프레임에서 처리 가능한 업데이트 횟수에는 상한을 둬서 브라우저 멈춤을 방지한다
- 결과 전용 시뮬레이션 모드도 동일한 고정 시간 간격과 동일한 전투 규칙을 사용한다
- 같은 seed, 스탯, AI 프로필, 규칙 버전이면 기기의 FPS와 관계없이 같은 결과를 재현할 수 있어야 한다

권장 구조 예시:

```js
const FIXED_DT = 1 / 60;
const MAX_STEPS_PER_RENDER = 5;

function frame(timestamp) {
  const elapsedSeconds = Math.min(
    (timestamp - previousTimestamp) / 1000,
    0.25
  );

  accumulator += elapsedSeconds;

  let steps = 0;

  while (
    accumulator >= FIXED_DT &&
    steps < MAX_STEPS_PER_RENDER
  ) {
    game.update(FIXED_DT);
    accumulator -= FIXED_DT;
    steps += 1;
  }

  renderer.render(game, accumulator / FIXED_DT);
  requestAnimationFrame(frame);
}
```

위 코드는 참고용이다. 실제 계획에서는 전투 상태 업데이트와 렌더링을 명확히 분리하라.

# 5. 캐릭터 스탯

준비 화면은 첫 구현에서 만들지 않는다.

그러나 이후 준비 화면에서 제한된 예산을 사용해 스탯을 증가시킬 예정이므로, 전투 시스템은 처음부터 스탯 객체를 입력으로 받아야 한다.

현재 고려 중인 스탯:

```js
const DEFAULT_STATS = {
  attackSpeed: 10,
  power: 10,
  maxHealth: 100,
  defense: 10,
  sharpness: 10,
  luck: 10,
  insight: 10
};
```

스탯의 종류, 초기값, 상한, 비용, 효과는 추후 바뀔 수 있다.

따라서 다음을 설계에 반영하라.

- 스탯 키와 기본값은 설정 파일 또는 데이터 객체에서 관리
- 전투 로직에 스탯 숫자를 직접 하드코딩하지 않음
- P1/P2가 독립적인 스탯 객체를 가짐
- 향후 스탯 투자 UI와 저장 데이터를 연결할 수 있어야 함
- `maxHealth`는 현재 전투 시작 체력 100 규칙과 충돌할 수 있으므로, 첫 구현에서의 처리 방식을 명확히 제안할 것
- `insight`의 구체적인 역할은 아직 확정되지 않았으므로, 첫 구현에서 적용하지 않거나 확장 포인트로만 남길지 권장안을 제시할 것

# 6. 전투 규칙

## 기본 조건

- P1과 P2 모두 사람이 조작하지 않는다
- P1과 P2 모두 시뮬레이션 AI가 조작한다
- 양쪽 AI는 동일한 AI 프레임워크와 전투 규칙을 사용한다
- 차이는 시작 위치, 바라보는 방향, 팀 색상, 캐릭터 스탯, AI 프로필로만 만든다
- P1은 링 왼쪽에서 시작하며 오른쪽을 바라본다
- P2는 링 오른쪽에서 시작하며 왼쪽을 바라본다
- 제한 시간의 초기값은 60초다
- 체력은 기본 규칙상 100에서 시작한다
- 체력이 0 이하가 되면 즉시 KO로 종료한다
- KO 승리 문구는 `RED COMET WIN!` 또는 `BLUE BULL WIN!`이다
- 제한 시간 종료 시 체력이 더 높은 선수가 판정승한다
- 제한 시간 종료 시 체력이 같으면 `DRAW`다
- 관전 모드에서는 R 키로 경기를 초기화하여 다시 시작할 수 있다

## 기본 행동

첫 구현에서 지원할 행동:

```js
const ActionType = {
  IDLE: "IDLE",
  APPROACH: "APPROACH",
  KICK: "KICK",
  PUSH: "PUSH",
  DROP_KICK: "DROP_KICK",
  ROPE_DROP_KICK: "ROPE_DROP_KICK"
};
```

각 공격 또는 행동에는 최소한 다음 속성이 필요하다.

- 시작 시간
- 유효 타격 구간
- 회복 시간
- 이동 가능 여부
- 이동 속도 또는 돌진 거리
- 공격 범위
- 히트박스
- 기본 피해량
- 넉백 세기
- 쿨다운
- `hasHit` 플래그
- 스프라이트 프레임 또는 포즈 연결

동일한 공격이 여러 업데이트 동안 중복 피해를 주지 않게 `hasHit`를 사용한다.

## 피격

- 공격자 히트박스와 상대 히트박스가 겹치면 피해를 준다
- 피격 시 짧은 경직이 발생한다
- 피격 시 공격 방향 반대쪽으로 넉백된다
- 선수는 서로 관통하지 않는다
- 선수는 링의 전투 가능한 좌우 경계를 넘을 수 없다
- 공격 중 또는 피격 중 상태 전이가 모순되지 않게 우선순위를 설계한다

## 피해량

첫 구현에서 아래 수식을 기본 후보로 사용한다.

```text
normalDamage = max(
  1,
  floor(
    attackBaseDamage
    + attacker.power * 0.6
    - defender.defense * 0.35
  )
)
```

치명타 확률 후보:

```text
criticalChance = clamp(
  0.05
  + attacker.sharpness * 0.01
  + attacker.luck * 0.003,
  0.05,
  0.45
)
```

치명타 피해:

```text
criticalDamage = floor(normalDamage * 1.5)
```

피해 표시:

- 일반 피해는 검은색 플로팅 숫자로 표시
- 치명타 피해는 붉은색 플로팅 숫자로 표시
- 치명타에는 가능하면 작은 `CRITICAL` 시각 효과를 표시
- 피해 숫자는 짧은 시간 동안 위로 떠오르고 투명해진 뒤 제거
- 랜덤 요소는 반드시 seed 기반 난수 생성기를 사용

Plan 모드에서 위 공식의 밸런싱 위험과 개선 필요 여부를 평가하라.
특히 기본 스탯 10에서 각 공격의 예상 피해량과 60초 전투의 평균 KO 가능성을 검토하라.

# 7. 분노 게이지 및 로프 드롭킥

각 선수는 0~100 범위의 분노 게이지를 가진다.

초기 분노 증가량 후보:

```text
일반 공격 명중: +8
일반 공격 피격: +12
치명타 명중: +14
치명타 피격: +18
로프 드롭킥 사용: -100
```

분노 게이지가 100이면 로프 드롭킥 사용 조건을 만족할 수 있다.

로프 드롭킥 규칙:

1. 분노 게이지가 100이어야 한다
2. 캐릭터가 링 가장자리 로프 근처에 있어야 한다
3. 상대가 반대 방향에 있어야 한다
4. 캐릭터는 로프를 이용해 짧은 반동 후 상대 방향으로 빠르게 돌진한다
5. 돌진 중 드롭킥을 수행한다
6. 일반 드롭킥보다 큰 피해량과 강한 넉백을 준다
7. 명중하지 못하면 짧은 회복 경직을 받는다
8. 사용 시 분노 게이지를 0으로 만든다

초기 피해량 후보:

```text
ropeDropkickDamage = normalDamage + 22
ropeDropkickCriticalDamage = floor(ropeDropkickDamage * 1.5)
```

Plan 모드에서 다음을 평가하라.

- 링 가장자리와 로프 근처 판정의 구현 방식
- 로프 반동 상태를 별도 상태로 분리해야 하는지
- AI가 로프 드롭킥을 시도할 때 필요한 최소 조건
- 무한 로프 왕복, 겹침, 경계 탈출 등의 예외 처리
- 60초 전투에서 분노 축적 속도가 적절한지

# 8. AI 규칙

P1과 P2는 모두 같은 시뮬레이션 AI 구조로 조작한다.

첫 구현에서는 공격 후보를 탐색하거나 점수화하지 않는다.
Utility AI, 행동 트리, 미래 예측, 최적 행동 탐색은 구현하지 않는다.

AI는 일정한 판단 주기마다 현재 가능한 행동 중 하나를 선택하는 단순한 FSM 기반 방식으로 구현한다.

## AI 상태

최소 상태 후보:

```js
const AIState = {
  IDLE: "IDLE",
  APPROACH: "APPROACH",
  ACTING: "ACTING",
  RECOVER: "RECOVER",
  HIT_STUN: "HIT_STUN",
  KO: "KO",
  TIMEOUT: "TIMEOUT"
};
```

필요하면 `ROPE_REBOUND` 또는 `RAGE_ATTACK` 같은 별도 상태를 추가할 수 있다.

## 행동 판단 주기

- AI는 매 프레임 새로운 행동을 선택하지 않는다
- 각 AI는 `decisionTimer`를 가진다
- `decisionTimer <= 0`일 때만 다음 행동을 선택한다
- 다음 판단 시간은 AI 프로필에 정의된 범위에서 seed 기반 난수로 결정한다
- 기본 판단 주기 후보는 0.20~0.50초다
- 공격 중, 피격 경직 중, KO 상태, 타임아웃 상태에서는 새 행동을 선택하지 않는다

## 행동 선택 규칙

1. 상대 거리가 `approachDistance`보다 멀면 `APPROACH`를 선택한다
2. 상대가 가까우면 현재 실행 가능한 일반 공격 목록을 만든다
3. 실행 가능한 일반 공격 중 하나를 seed 기반 난수로 균등 선택한다
4. 일반 공격이 불가능하면 `IDLE` 또는 `APPROACH`를 선택한다
5. 분노가 100이고 로프 드롭킥 조건을 만족하면 설정된 확률로 `ROPE_DROP_KICK`을 선택한다
6. 선택된 행동이 쿨다운, 거리, 경직, 로프 위치 조건 때문에 실행 불가능하면 안전한 대체 행동으로 전환한다
7. 두 AI가 동시에 공격할 수 있으며, 동시 피격 및 동시 KO 가능 여부를 명확히 결정한다

## AI 프로필

초기 구조 예시:

```js
const AI_PROFILES = {
  normal: {
    decisionIntervalMin: 0.20,
    decisionIntervalMax: 0.50,
    approachDistance: 220,
    ropeDropkickChance: 0.85,
    actionWeights: {
      KICK: 1,
      PUSH: 1,
      DROP_KICK: 1
    }
  }
};
```

첫 구현에서는 일반 공격을 균등 무작위 선택한다.

그러나 나중에 난이도를 조절할 수 있도록 다음은 설정 객체에 남겨 둔다.

- 판단 주기
- 반응 지연
- 행동별 가중치
- 행동 실패 확률
- 로프 드롭킥 사용 확률
- 공격 사거리 오차
- 공격 쿨다운 보정
- 피격 후 재접근 성향

AI 프로필과 캐릭터 스탯은 반드시 분리한다.

# 10. 결과 전용 시뮬레이션 모드

결과 전용 모드는 전투 애니메이션을 보여 주지 않거나 최소화하고, 동일한 전투 규칙으로 결과만 빠르게 계산한다.

중요 원칙:

- 관전 모드와 결과 전용 모드는 동일한 `GameState`, `CombatRules`, `AIController`, RNG, 고정 시간 업데이트를 공유한다
- 렌더링 유무만 달라야 한다
- 같은 seed, 같은 스탯, 같은 AI 프로필, 같은 규칙 버전이면 양쪽 모드의 결과가 같아야 한다
- 시뮬레이션 중 `Math.random()`을 직접 사용하지 않는다

필수 기능:

```text
결과만 1회 실행
100회 시뮬레이션
1,000회 시뮬레이션
결과 JSON 다운로드
```

대량 시뮬레이션 요구:

- 브라우저 UI가 장시간 멈추지 않게 한다
- 첫 구현에서는 배치 처리 또는 `setTimeout`, `requestIdleCallback` 등의 방식으로 나눠 실행하는 방안을 검토한다
- Web Worker는 첫 구현에서 필수는 아니지만, 이후 10,000회 이상 실행을 위한 확장 방향으로 설계에 고려한다
- 실행 중 진행률, 취소 가능 여부, 실패 처리 방안을 제안한다
- 1,000회 시뮬레이션에서 메모리가 과도하게 증가하지 않게 개별 상세 로그의 보관 정책을 제안한다

# 11. 재현성 및 난수

시뮬레이션 결과 비교와 밸런싱 회귀 테스트가 프로젝트의 핵심이다.

반드시 아래를 만족해야 한다.

- seed 기반 의사 난수 생성기를 구현한다
- `Math.random()`을 직접 사용하지 않는다
- 같은 seed와 같은 설정에서는 같은 행동 순서, 같은 피해, 같은 승패 결과가 나와야 한다
- 관전 모드와 결과 전용 시뮬레이션 모드의 결과가 일치해야 한다
- 각 경기 결과에는 seed를 기록한다
- 다회 시뮬레이션은 시작 seed와 매치별 파생 seed 정책을 기록한다
- 결과 데이터에는 `rulesVersion`, `aiProfileVersion`을 기록한다
- 난수는 최소한 행동 선택, 판단 주기, 치명타 판정, 향후 행동 실패 확률에 사용한다

Plan 모드에서 브라우저 환경에 적절한 간단한 seed RNG 방식을 제안하라.

# 13. 미래 엔지니어링 루프

이 프로젝트는 아래 반복 과정을 핵심 개발 루프로 삼는다.

```text
캐릭터 스탯 및 AI 프로필 설정
    ↓
동일 시드 또는 다수 시드로 N회 자동 전투 실행
    ↓
승률, KO 비율, 평균 전투 시간, 피해량,
치명타 수, 로프 드롭킥 성공률 집계
    ↓
목표 난이도와 실제 결과 비교
    ↓
스탯, 피해 공식, AI 파라미터, 행동 가중치,
판단 주기, 반응 지연 조정
    ↓
동일 조건 및 동일 시드로 재실행
    ↓
수정 전후 결과 비교
    ↓
관전 모드에서 전투 흐름이 자연스러운지 확인
```

예시 난이도 목표:

```text
쉬움: 기준 캐릭터와 비교한 P1 승률 약 65~75%
보통: 기준 캐릭터와 비교한 P1 승률 약 45~55%
어려움: 기준 캐릭터와 비교한 P1 승률 약 25~35%
```

Plan 모드에서 이 목표가 현재 “P1과 P2 모두 AI” 구조와 어떻게 연결되어야 하는지 평가하라.
필요하다면 “기준 AI vs 난이도 AI” 또는 “기준 스탯 vs 조정 스탯”으로 명확히 정의하는 방안을 제시하라.
