# 05. 경기 일치성 및 카운터 우선순위 수정 계획

작성일: 2026-07-30  
관련 문서: `docs/todo.md`  
대상: 버그 픽스 4건  
목표: 관전과 단일 headless 결과가 동일한 경기 설정을 사용하도록 보장하고, 설정/전투 화면 전환을 한 프레임 안에서 통일하며, 간파 효과를 검증 가능하게 만들고 동시 공격에서 카운터를 우선 처리한다.

## 1. 요구사항 요약

- 현재 재생한 전투와 `결과만 1회`가 같은 seed·스탯으로 동일한 결과를 내도록 수정한다.
- 스테이터스 설정 화면과 전투 화면을 같은 크기·비율의 영역에서 자연스럽게 전환한다.
- 간파 스탯이 실제 카운터와 시뮬레이션 결과에 반영되는지 확인하고 효과를 확인할 수 있게 한다.
- 같은 tick에 일반 공격과 카운터가 함께 성립하면 카운터를 우선하고 해당 선수의 일반 공격은 발동하지 않게 한다.
- 회피 스탯 추가 또는 moveSpeed의 회피 부가 효과는 검토만 하고 이번 구현 계획에는 포함하지 않는다.

## 2. 우선 버그 픽스

### 관전과 `결과만 1회`의 경기 설정 통일

**관련 TODO:** 버그 픽스 1

**재현 및 원인**

- 코어의 같은 seed·같은 스탯 관전/headless 결과는 현재 자동 테스트에서 일치한다.
- UI는 관전 시작 때 `seed-input` 값을 읽어 Game을 만들지만 `결과만 1회`를 누를 때 입력값을 다시 읽는다. 전투 도중 seed를 수정하면 관전 중인 경기와 단일 headless가 서로 다른 seed를 사용한다.
- 관전 시작 당시 설정을 별도 객체로 표시·보관하지 않고 완료된 관전 결과도 저장하지 않아, 사용자가 실제로 비교한 두 경기의 seed·스탯 provenance를 확인하기 어렵다.
- 결과 JSON의 `mode`는 관전과 simulation에서 의도적으로 다르므로 전체 JSON 단순 비교도 항상 불일치한다.

**수정 방안**

- 관전 생성 시 `{ seed, p1Stats, p2Stats, rulesVersion, statRulesVersion }`을 불변 `activeMatchConfig`로 저장한다. 재시작 전까지 입력 UI 변경은 현재 경기에 영향을 주지 않는다.
- seed 입력 옆에 `현재 경기 seed`를 별도로 표시하고 경기 진행 중에는 입력을 잠근다. `관전 시작` 또는 `재시작` 때만 새 입력값을 snapshot으로 확정한다.
- `결과만 1회`는 현재 입력값을 다시 읽지 않고 `activeMatchConfig`를 그대로 사용한다. 설정 화면에서 전투로 처음 진입한 경우에도 같은 snapshot으로 관전과 단일 실행을 만든다.
- 관전 종료 시 `game.getResult()`를 `lastSpectatorResult`에 저장한다. 단일 headless 결과와 비교할 때 표현 메타데이터인 `mode`만 제외한 canonical combat result를 사용한다.
- 비교가 일치하면 상태 줄에 `관전 결과와 일치`를 표시한다. 불일치하면 두 결과를 덮어쓰지 않고 seed·버전·스탯 snapshot과 최초 차이 필드를 오류로 표시한다.
- 100/1,000회 배치는 기존처럼 입력한 base seed에서 파생하되 시작 순간 설정 snapshot을 고정한다.

**위험과 검증**

- 관전 완료 전 단일 실행을 요청해도 같은 active snapshot으로 headless 결과를 만들며, 관전 완료 후 자동 비교한다.
- seed 입력 변경, 설정 화면 왕복, 재시작, pause/resume, 1회 버튼의 순서를 바꿔도 active config가 의도한 시점에만 교체되는지 UI 상태 테스트를 작성한다.
- 100개 seed와 여러 스탯 조합에서 관전/headless canonical 결과가 일치하고, seed를 전투 중 수정해도 현재 경기 비교에는 영향을 주지 않는지 검사한다.

### 설정과 전투를 동일한 화면 프레임에서 전환

**관련 TODO:** 버그 픽스 2

**재현 및 원인**

- 현재 설정 화면은 콘텐츠 높이에 따라 늘어나는 2열 grid이고, 전투 Canvas만 별도의 16:9 `game-stage`다. 두 화면의 외곽 크기와 비율이 달라 전환 시 아래 콘텐츠가 크게 이동한다.
- `hidden`으로 서로 다른 블록을 즉시 교체해 크기 보간이나 시각적 연결이 없다.

**수정 방안**

- 제목 아래에 공통 `experience-frame`을 만들고 desktop에서 `aspect-ratio: 16 / 9`, 동일 border·background·shadow를 적용한다.
- 설정 화면과 Canvas 전투 화면을 프레임 내부의 절대 배치 layer로 겹친다. 설정 화면은 내부 논리 2열 layout을 유지하되 프레임 높이를 넘으면 layer 내부에서만 스크롤한다.
- 화면 전환은 `data-view="setup|battle"` 상태 하나로 관리하고 180ms opacity와 짧은 translate 전환을 적용한다. 전환 중 비활성 layer에는 `pointer-events: none`, `aria-hidden="true"`를 적용한다.
- 전투 조작과 headless 패널은 공통 프레임 아래에 유지하되 battle view에서만 표시한다. 설정↔전투 전환 시 제목과 공통 프레임 위치는 움직이지 않는다.
- 760px 이하에서는 공통 프레임의 aspect ratio를 해제하고 최소 높이를 사용해 설정 항목 접근성을 확보한다. 가로 모바일 전투 Canvas는 16:9를 유지한다.

**위험과 검증**

- 설정 내용 축소로 버튼이 지나치게 작아지지 않도록 44px 터치 영역을 유지하고 필요할 때 내부 스크롤을 허용한다.
- desktop 1440/1024px, 가로 모바일, 세로 모바일에서 설정·전투 외곽 bounding rect가 같은지 DOM 테스트 및 육안 검사한다.
- 빠르게 왕복해도 이중 입력, 숨은 버튼 focus, Canvas 크기 변경이나 스크롤 점프가 없는지 확인한다.

### 간파 적용 확인과 관측성 보강

**관련 TODO:** 버그 픽스 3

**확인 결과**

- 간파는 `clamp(0.05 + insight × 0.01, 0.05, 0.45)`로 counter RNG 판정에 적용되어 있다.
- seed 0~999, 고정 Blue Bull 조건에서 P1 간파 10은 7,936회 시도 중 1,169회 성공(14.73%), 간파 20은 7,852회 중 1,922회 성공(24.48%)했다.
- 같은 실험의 P1 승률은 57.9%에서 65.8%로 상승했다. 규칙 누락은 재현되지 않았으며 현재 문제는 단일 결과 화면에서 시도·성공·성공률을 알아보기 어려운 점이다.

**수정 방안**

- 설정 미리보기의 카운터 확률은 계속 공통 `deriveStats()` 값을 사용한다.
- 단일 결과 요약에 양측 `카운터 시도`, `카운터 성공`, `카운터 성공률`을 표시한다. 배치 요약에도 기존 평균 카운터 외에 성공률을 표시한다.
- JSON의 `rawStats.insight`, `derivedStats.counterChance`, `countersAttempted`, `countersSucceeded`를 하나의 검증 경로로 테스트한다.
- 통계 변동을 고려해 정확한 발생 횟수보다 고정 RNG 단위 테스트와 1,000 seed 민감도 테스트를 사용한다. 간파 20의 성공률이 간파 10보다 유의하게 높고 각각 목표 확률 주변에 있는지 확인한다.

**위험과 검증**

- 로프 드롭킥 카운터 면역과 pending counter 중 추가 카운터 차단 때문에 `countersAttempted` 수 자체는 스탯별로 달라질 수 있다. 성공 횟수만 비교하지 않고 `succeeded / attempted`를 비교한다.
- 간파 변경이 AI·치명타 RNG 순서에 영향을 주지 않도록 독립 counter RNG를 유지한다.

### 동시 일반 공격보다 카운터 우선

**관련 TODO:** 버그 픽스 4

**재현 및 원인**

- Game은 같은 tick의 양측 hit 후보를 먼저 수집하지만 `applyHits`가 후보를 배열 순서대로 즉시 처리한다.
- P1의 공격을 P2가 카운터해도 이미 수집된 P2의 일반 공격 후보가 뒤이어 적용된다. 결과적으로 P2의 일반 공격 피해와 18 tick 뒤 카운터 피해가 모두 발생할 수 있다.

**수정 방안**

- hit 처리를 `판정 단계 → 우선순위 단계 → 적용 단계`의 3단계로 바꾼다.
- 판정 단계에서 모든 일반 공격 후보의 카운터 성공 여부를 독립 RNG로 먼저 확정한다. 로프 드롭킥과 이미 pending counter인 선수는 기존처럼 카운터 판정을 하지 않는다.
- 카운터에 성공한 선수 ID를 집합으로 만든다. 해당 선수가 같은 tick에 제출한 일반 공격 후보는 우선순위 단계에서 취소한다.
- 카운터된 원래 공격도 취소하고 `COUNTER_TRIGGERED`와 pending counter만 남긴다. 따라서 한 선수에게는 같은 tick의 일반 공격 또는 카운터 중 카운터 하나만 선택된다.
- 양측이 서로 카운터에 성공하면 양측 일반 공격을 모두 취소하고 두 pending counter를 유지한다. 이는 각 선수별 우선순위 규칙을 대칭적으로 적용한 결과이며 P1/P2 배열 순서로 한쪽을 임의 우선하지 않는다.
- 취소된 일반 공격은 `attacksAttempted`에는 남지만 `attacksHit`, 피해, 분노와 hit 이벤트에는 포함하지 않는다. 필요 시 디버깅용 `ACTION_CANCELLED` 이벤트만 기록한다.

**위험과 검증**

- 한쪽 카운터 성공 시 양측 일반 피해 0, 18 tick 뒤 카운터 피해 1회인지 확인한다.
- 양쪽 카운터 성공, 한쪽만 성공, 양쪽 실패, 로프 드롭킥 포함 동시 공격을 각각 고정 RNG로 테스트한다.
- 동시 KO와 counter delay, 카운터 성공 지표, 독립 RNG 소비 순서 및 같은 seed 재현성을 회귀 검사한다.
- 전투 규칙 의미가 바뀌므로 `rulesVersion`을 올리고 1,000경기 승률·KO율·카운터 빈도를 이전 기준과 비교한다.

## 3. 검토 필요 — 회피 효과

**관련 TODO:** 검토 필요 1 — 이번 구현 계획에는 반영하지 않음

- **새 회피 스탯:** 역할이 명확하고 moveSpeed와 독립 튜닝이 가능하지만 10점 예산에 새 경쟁 항목이 추가되고 defense·insight와 생존 역할이 겹친다. 설정 UI, 결과 스키마, RNG 스트림과 전투력 공식도 확장해야 한다.
- **moveSpeed 부가 효과:** 현재 승률 기여가 약한 moveSpeed를 보완하고 민첩성이라는 테마가 자연스럽다. 반면 한 스탯이 이동·로프 거리·완전 회피까지 제공해 복합 가치가 급격히 커질 수 있다.
- **공통 위험:** 데미지 0 회피는 카운터와 달리 반격하지 않더라도 피해·경직·넉백·분노를 어디까지 무효화할지 결정해야 한다. 별도 RNG를 사용하지 않으면 기존 카운터/치명타 결과도 바뀐다.
- **권장안:** 별도 스탯을 추가하지 않고 moveSpeed 10 초과분에만 `min((moveSpeed - 10) × 0.5%p, 5%)`의 낮은 회피율을 제공하는 안을 후속 검토한다. 효과가 약한 스탯을 보완하면서 상한 5%로 카운터와 역할 중복을 제한할 수 있다. 승인 전에는 구현하지 않는다.
- 구현을 검토할 때는 회피 성공 시 피해·경직·넉백은 0, 공격자/방어자 분노 증가는 없음, `DODGE` 이벤트 표시, 카운터보다 먼저 판정하지 않도록 별도 규칙 결정을 권장한다.

## 4. 완료 기준

- 새 계획 문서 첫 부분에 위 `요구사항 요약`이 유지된다.
- 현재 관전과 `결과만 1회`가 동일한 active match config를 사용하고 canonical 결과가 100개 seed에서 일치한다.
- 설정과 전투 view의 공통 프레임이 desktop에서 같은 16:9 bounding rect를 유지하며 자연스럽게 전환된다.
- 간파 10/20의 설정 미리보기와 실제 counter 성공률이 각각 약 15%/25% 방향으로 일치하고 단일·배치 UI에서 확인할 수 있다.
- 동시 공격에서 카운터 성공자의 일반 공격은 취소되고 카운터만 18 tick 뒤 한 번 적용된다.
- 기존 24개 자동 테스트와 결정성, 관전/headless 일치, 링 경계, 로프 드롭킥 카운터 면역, 스탯 snapshot 테스트를 모두 유지한다.
- 변경된 결과 비교 방식, 화면 전환과 카운터 우선순위를 `README.md`에 기록한다. `docs/todo.md`는 별도 사용자 지시 없이 수정하지 않는다.
